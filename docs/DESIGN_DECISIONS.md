# Design decisions

An ADR-style log of the main decisions in this repository. Each entry records the context, the decision, the consequences, and the alternatives considered. Decisions here are not final: if one changes, add a new entry that supersedes it instead of editing history.

## ADR 1: Scripts use only the Python standard library

**Status:** Accepted | **Date:** 2026-10-07

**Context.** The scripts must run wherever the skill is installed (a developer laptop, a sandbox, a CI job) without a setup step. Agents often cannot install packages, and users should not have to manage a virtual environment to get a wireframe.

**Decision.** Every script under `project-blueprint/scripts/` imports only the standard library and supports Python 3.10 or newer. Validation in the renderer is hand-written instead of using `jsonschema`. `pytest` and `jsonschema` are allowed as development dependencies only, listed in `requirements-dev.txt`, and are used by the test suite to check the schemas and examples.

**Consequences.** Nothing to install for users. The cost is more code than a library would need (a table parser, an SVG writer, a validator) and fewer features than a full Markdown or schema library. The JSON schemas and the renderer's validation can drift apart; tests check both against the same example.

**Alternatives.** Use `jsonschema`, a Markdown parser, or an SVG library at runtime (rejected: needs installation); rewrite the scripts in Node (rejected: we assume Python is more commonly available in agent environments, but we have not verified that).

## ADR 2: Mermaid as the diagram format

**Status:** Accepted | **Date:** 2026-10-07

**Context.** Diagrams should live in the user's repository, be reviewable in pull requests, and need no external tool to view.

**Decision.** All flowcharts, sequence, ER, state, class, and Gantt diagrams are Mermaid text in fenced code blocks inside Markdown files. A validator script checks them.

**Consequences.** Diagrams are plain text, so they diff well and GitHub renders them in Markdown. Layout is automatic and cannot be tuned by hand, and Mermaid's parser is picky about quoting. Without `mmdc` installed, the validator can only check heuristically and cannot prove a diagram renders.

**Alternatives.** PlantUML (needs a Java runtime or server), draw.io or Excalidraw files (binary or verbose JSON, poor diffs), images generated by a script (not editable as text).

## ADR 3: Wireframes as JSON rendered to SVG by our own renderer

**Status:** Accepted | **Date:** 2026-10-07

**Context.** Wireframes need to be quick for an agent to produce and correct, consistent across screens, and viewable anywhere. Hand-written SVG is long and easy to get wrong.

**Decision.** The agent writes a compact JSON spec (screens, elements, navigation). `render_wireframe.py` turns it into one SVG per screen, an optional HTML gallery, and a screen-flow diagram. Rendering is deterministic (same spec, same bytes) and uses a simple vertical layout with grayscale low-fidelity styling.

**Consequences.** Specs are short and diffable, errors point to a JSON path, and navigation can be checked for unreachable screens. The look is deliberately basic and the layout engine is limited (stacked elements, row and column nesting up to three levels). The spec format is also reusable by a future web app.

**Alternatives.** Agent-written raw SVG or HTML (long, inconsistent), exporting to a design tool format (heavier, not text-first), screenshots of rendered HTML (needs a browser).

## ADR 4: `profile.json` as the single source of truth

**Status:** Accepted | **Date:** 2026-10-07

**Context.** Several artifacts describe the same project. If each one is generated straight from the code, the screen names, entities, and ids drift apart.

**Decision.** The scanner produces a draft, the agent merges it into `blueprint/profile.json` (validated against a schema), and every artifact is generated from the profile. Ids are lowercase-kebab and reused everywhere. Everything inferred is marked `inferred` or recorded as an `ASSUMPTION:`.

**Consequences.** Artifacts stay consistent and a correction in one place propagates. The profile becomes the critical file: a wrong profile spreads everywhere, so the quality checklist verifies other artifacts against it. A changed profile makes older artifacts stale, which is why each generated file carries the profile hash.

**Alternatives.** Generate each artifact independently from the code (drift), or keep the knowledge only in the conversation (not versioned, lost between sessions).

## ADR 5: Never overwrite existing files

**Status:** Accepted | **Date:** 2026-10-07

**Context.** Users edit generated artifacts. A rerun that silently replaces their edits destroys work and erodes trust in the tool.

**Decision.** The agent writes only inside `blueprint/`. If a target file exists it asks first, or writes the new version with a `-v2` suffix. The analyzer writes only to its `--out` directory.

**Consequences.** Reruns are safe, and the user can compare versions. The folder can accumulate `-v2`, `-v3` files that someone must clean up, and the agent has to check for existing files before every write.

**Alternatives.** Always overwrite (risky), keep timestamped backups (clutter), or rely on git alone (not every project is a git repository).

## ADR 6: Regex extractors instead of parsers in the analyzer

**Status:** Accepted | **Date:** 2026-10-07

**Context.** The scanner should give the agent a useful head start across many stacks (ASP.NET, Express, Flask, FastAPI, Next.js) without language-specific tooling and without executing project code.

**Decision.** Lightweight regular-expression extractors find routes, views, and entities. Each extractor is a separate function, every extracted item is marked `inferred: true`, and a failing extractor or file is logged as a warning without stopping the scan. The references document what each extractor misses (for example mounted routers and Django `urls.py`), so the agent reads those parts by hand.

**Consequences.** Broad coverage with no dependencies and safe operation on untrusted code. The results are drafts: they can miss routes or report wrong ones, which is why they are never used without review.

**Alternatives.** Real parsers per language (heavy, many dependencies), running the app to list its routes (executes untrusted code), or leaving all extraction to the model (slow and inconsistent on large projects).

## ADR 7: The sprint table is a strict, parsed format

**Status:** Accepted | **Date:** 2026-10-07

**Context.** Sprint plans are most useful when they can be imported into Jira, Trello, or GitHub Projects, and checked automatically for mistakes such as oversized stories or circular dependencies.

**Decision.** Sprint plans contain Markdown tables with a fixed header. `export_sprint.py` parses them, validates points, priorities, dependencies, and sprint numbers, warns about capacity, and exports CSV and JSON. The column names must not change.

**Consequences.** Plans are both human-readable and machine-checked, and mistakes surface as errors with line numbers. The format is rigid: one-line cells, a fixed estimate scale, and no extra columns.

**Alternatives.** Free-form prose plans (no validation or export), or JSON as the primary format (harder for people to read and edit).
